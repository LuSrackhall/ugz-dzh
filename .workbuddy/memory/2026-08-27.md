## 打印版跨平台尺寸不一致诊断（Mac WPS 正常 / Windows WPS 走样）

- **根因（已实测 styles.xml 证实）**：列宽是"字符"单位，渲染像素 = 字符 × Normal 默认字体 MDW + 5px。
  文件 Normal 默认字体 = **Calibri 11**（excelize 默认，从未显式锁），Mac 上 Calibri 缺失 fallback、
  Windows 上有真 Calibri → 两端 MDW 不同 → 同值列宽像素不同 → 整表非均匀错位（每列 +5px 固定，
  大列偏差多小列少）。
- **数字字体 Noteworthy（GL 7pt / ML 6pt）是 macOS 专有字体，Windows 缺失 fallback** → 数字观感/占宽失控。
  代码点：print_gl.go:85、print_ml.go:92（dataFontFamily）。
- 标题"仿宋"（print_gl.go:122、print_ml.go:119）Windows 有、Mac fallback，风险低于 Noteworthy。
- 打印层附加因素：paperSize=13 B5(JIS) 个别 Windows 驱动映射成 B5(ISO)；物理打印边缘两端不同。
  固定缩放 74% + 显式分页符已锁死分页逻辑，无需改。

## 修复方案（用户暂缓，先讨论；结论：方案 A 为正解）

- **方案 A（根治）**：① 删 print_gl.go:85 / print_ml.go:92 的 dataFontFamily（数字统一宋体）；
  ② `SetDefaultFont("宋体")` 锁 Normal → 两端 MDW 一致。代价：现有像素补偿参数
  （edgePixelDelta / nonAmountPixelDelta / amountColPixel / edgePixel，反推系数 (px-5)/7 假设
  MDW=7）需按宋体实际 MDW 重调，两端目测验收。
- **方案 B（止血）**：只删 Noteworthy，列宽基准问题仍在，不解决根本问题。
- **验证手段**：LibreOffice Calc（Mac 上）独立字体引擎可模拟 Windows fallback 行为作预检；
  两端"打印为 PDF"对比表格线物理位置；建议做标尺测试表。打印时 Windows WPS 手动选 B5(JIS)、
  缩放选"实际大小"勿选"适应页面"。

## 跨平台排查终局结论（21:50 最终定论）

- **Mac 原版（Normal=Calibri）在 WPS 里的实际替换字体 ≠ CoreText 的 Helvetica**：CoreText 测 CTFontCreateWithName("Calibri")→Helvetica（数字宽 1139/2048=8.157px@11pt），但用户实测"Normal=Arimo(8.157px) 的测试版在 Mac 上与原版尺寸对不上"→ **证明 WPS Mac 有独立字体替换机制（extfontlist.json 加密），Mac 原版真实 MDW ≠ 8.157px，系统层测不到**。"匹配 Mac 原版 MDW"路线因缺关键数据彻底关闭。
- **已试 27 个字体 + MDW 匹配方案全部失败 → 唯一可靠路线 = 两端安装同一字体文件（如 Arimo，数字宽 8.157px 与 Arial/Helvetica 完全一致），Mac 版也换掉 Calibri，两端同一文件 MDW 必然一致 → 列宽绝对对齐**。代价：Mac 列宽基准变（Calibri→Arimo），像素补偿参数需一次性重调，之后两端永久一致。
- Arimo 完整版（含中文）待下载；fontsource 的 latin subset 已验证可用（数字 0-9 等宽 1139/2048）。下载源：jsdelivr @fontsource/arimo woff2→fontTools 解压（GitHub raw/SourceForge/Debian 均被反爬）。
- 用户决策待定：接受"两端统一字体+Mac 重调一次"（推荐，永久一致） vs 保持现状（Mac 为准，Win 打印手动补偿）。
